escalation_ladder.py
# climb only when the rung below is measured and failing
def customize(task, evals):
    if evals.pass_with(prompt_engineering):   # minutes, API only
        return "prompt"
    if task.needs_fresh_or_private_facts:     # real-time data
        return "rag"
    if task.needs_locked_in_behavior:         # style, schema, reasoning
        return "sft"                          # LoRA / QLoRA
    if task.has_preference_pairs:             # chosen vs rejected
        return "dpo | orpo"
    return "combine(rag, sft)"               # most prod systems

Eval before you train

No held-out eval set, no fine-tune. If you cannot score the base model, you cannot prove the tuned one is better.

Data beats hyperparameters

A few hundred clean, consistent examples outperform thousands of noisy ones. Fix the dataset before touching learning rate.

Check the verify per model tags

Bedrock hyperparameters, schemas and model support differ per base model and region, and TRL arguments shift between releases. Confirm against current docs.

Fine-tuning frameworks & execution layers

Two ways to get a customized model: hand AWS a dataset and a role (Bedrock), or own the training loop on your GPUs (TRL). Same goal, very different control surface.

Amazon Bedrock customization

control plane: bedrock · inference plane: bedrock-runtime

You supply data, a role and hyperparameters. AWS provisions the training compute, runs the job, and returns a custom model ARN. You never see GPUs, containers or the training loop.

Step 3 · Provision the job, then serve it

bedrock_customize.py
import boto3, time
bedrock = boto3.client("bedrock", region_name="us-east-1")

# which base models can be fine-tuned in this region?
ok = bedrock.list_foundation_models(byCustomizationType="FINE_TUNING")["modelSummaries"]

job = bedrock.create_model_customization_job(
    jobName="ft-support-v1",
    customModelName="support-assistant-v1",
    roleArn="arn:aws:iam::<ACCOUNT_ID>:role/BedrockCustomizationRole",
    baseModelIdentifier="<BASE_MODEL_ID_FROM_LIST_ABOVE>",
    customizationType="FINE_TUNING",
    trainingDataConfig={"s3Uri": "s3://BUCKET/ft/train/train.jsonl"},
    validationDataConfig={"validators": [{"s3Uri": "s3://BUCKET/ft/val/val.jsonl"}]},
    outputDataConfig={"s3Uri": "s3://BUCKET/ft/output/"},
    hyperParameters={            # values are STRINGS; names vary per base model
        "epochCount": "2",
        "batchSize": "1",
        "learningRate": "0.00001",
        "learningRateWarmupSteps": "5",
    },
)

while True:
    s = bedrock.get_model_customization_job(jobIdentifier=job["jobArn"])
    if s["status"] in ("Completed", "Failed", "Stopped"): break
    time.sleep(60)

# custom models are served through Provisioned Throughput
pt = bedrock.create_provisioned_model_throughput(
    provisionedModelName="support-assistant-v1-pt",
    modelId=s["outputModelArn"],
    modelUnits=1,                # add commitmentDuration="OneMonth" | "SixMonths" for discount
)
# then: bedrock-runtime.converse(modelId=pt["provisionedModelArn"], ...)

Managed job vs AWS Serverless AgentCore

These are different layers. A customization job changes the model. Amazon Bedrock AgentCore is a serverless runtime for hosting agents (runtime, identity, gateway, memory, observability). It does not train anything. They meet at the end: the agent running in AgentCore calls your custom model ARN as its reasoning engine.

// 02

Core ML & PEFT architecture

Parameter-efficient fine-tuning trains a tiny set of new weights and leaves the pre-trained model frozen. Cheaper, faster, and far less likely to overwrite what the model already knows.

Transfer learning & base implementations

the base model carries the logic; tuning only nudges it

A pre-trained foundation model already encodes language, world knowledge and reasoning patterns. Fine-tuning does not teach those from scratch. It shifts the output distribution toward your domain, format and style using far less data than pre-training.

ConcernBedrockHugging Face TRL
Model accessOpaque. You name a baseModelIdentifier; weights are never exposed.Explicit. AutoModelForCausalLM loads every layer; you can inspect, freeze or swap them.
What gets trainedDecided by AWS for that base model.You choose layers via target_modules, rank, dropout, full vs PEFT.
Pipeline shapeSingle API call, isolated managed pipeline.Composable stages: SFT → preference → merge → quantize.
DebuggingLoss CSVs in S3; limited visibility.Per-step logs, gradient norms, checkpoints, custom callbacks.

LoRA & QLoRA configuration

W′ = W + (α / r) · B·A  ·  W frozen, only A and B train

TRL + peft + bitsandbytes (QLoRA, 4-bit NF4)

qlora_sft.py
import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from trl import SFTConfig, SFTTrainer

MODEL = "meta-llama/Llama-3.1-8B-Instruct"

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",            # NormalFloat4
    bnb_4bit_use_double_quant=True,       # quantize the quant constants too
    bnb_4bit_compute_dtype=torch.bfloat16,
)
tok = AutoTokenizer.from_pretrained(MODEL)
tok.pad_token = tok.pad_token or tok.eos_token

model = AutoModelForCausalLM.from_pretrained(
    MODEL, quantization_config=bnb, device_map="auto", torch_dtype=torch.bfloat16)

lora = LoraConfig(
    r=16,                                 # rank: 8-64 typical
    lora_alpha=32,                        # scale = alpha / r  (2x rank is a common start)
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj"],   # all linear = best quality
)

cfg = SFTConfig(
    output_dir="out/sft",
    num_train_epochs=2,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,        # effective batch = 4 x 8 x n_gpus
    learning_rate=2e-4,                   # LoRA tolerates ~10x full-FT LR
    lr_scheduler_type="cosine",
    warmup_ratio=0.03,
    optim="paged_adamw_8bit",
    bf16=True,
    gradient_checkpointing=True,
    logging_steps=10,
    eval_strategy="steps", eval_steps=50,
    save_strategy="steps", save_steps=50, save_total_limit=3,
    load_best_model_at_end=True, metric_for_best_model="eval_loss",
    report_to="wandb",
    packing=False,
)

train = load_dataset("json", data_files="train.jsonl", split="train")
val   = load_dataset("json", data_files="val.jsonl",   split="train")

trainer = SFTTrainer(model=model, args=cfg, train_dataset=train, eval_dataset=val,
                     peft_config=lora, processing_class=tok)
trainer.train()
trainer.save_model("out/sft/adapter")     # adapter only: tens of MB
// knobsr sets adapter capacity. alpha scales its influence. target_modules decides where it attaches. Raise rank only if the loss plateaus high. Keep the base model's pad_token and chat template consistent with inference.
// QLoRA vs LoRAQLoRA stores the frozen base in 4-bit to fit large models on one GPU, at a modest speed cost. If the model fits in bf16, plain LoRA is faster and slightly cleaner.

How Bedrock handles LoRA internally

  • Base weights stay static. Your job never rewrites the foundation model; what you receive is a customized variant tied to that base.
  • AWS manages the adapter. For models where Bedrock uses parameter-efficient methods, rank, target layers and optimizer details are chosen by the service. You influence them only through the exposed hyperparameters some Nova models expose an adapter-rank style setting; verify.
  • Artifacts stay in AWS-managed storage. You get a custom model ARN plus metrics written to your output S3 prefix, not downloadable weights.
  • Portability trade-off. Bedrock-customized models run only on Bedrock. If you need to move, train with TRL and import the merged safetensors instead.

PyTorch under the hood

TRL and transformers.Trainer are thin layers over PyTorch · Bedrock exposes none of this

Every TRL trainer ends up running the same PyTorch loop: forward pass, loss on label tokens, backward(), optimizer step, scheduler step. Knowing the primitives lets you debug OOMs, NaNs and slow throughput, and drop to custom losses when a stock trainer does not fit.

The minimal loop (what trainer.train() does)

pytorch_sft_loop.py
import math, torch
from transformers import get_cosine_schedule_with_warmup

# labels = input_ids copy with prompt / padding positions set to -100 (ignored by the loss)
# so you train only on assistant tokens
model.train()
params = [p for p in model.parameters() if p.requires_grad]   # LoRA params only
opt = torch.optim.AdamW(params, lr=2e-4, weight_decay=0.0)

ACCUM, EPOCHS = 8, 2
total = (len(train_loader) // ACCUM) * EPOCHS
sched = get_cosine_schedule_with_warmup(opt, int(0.03 * total), total)

for epoch in range(EPOCHS):
    for i, batch in enumerate(train_loader):       # input_ids, attention_mask, labels
        batch = {k: v.to(model.device) for k, v in batch.items()}
        with torch.autocast("cuda", dtype=torch.bfloat16):
            loss = model(**batch).loss / ACCUM      # HF shifts labels + masks -100 internally
        loss.backward()
        if (i + 1) % ACCUM == 0:
            torch.nn.utils.clip_grad_norm_(params, 1.0)
            opt.step(); sched.step()
            opt.zero_grad(set_to_none=True)

# validation: no grads, eval mode, perplexity = exp(mean loss)
model.eval()
with torch.no_grad():
    losses = [model(**{k: v.to(model.device) for k, v in b.items()}).loss.item() for b in val_loader]
print("val loss", sum(losses) / len(losses), "ppl", math.exp(sum(losses) / len(losses)))

LoRA from scratch (to see what peft injects)

lora_linear.py
import math, torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=16, alpha=32, dropout=0.05):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad_(False)                       # W stays frozen
        self.A = nn.Parameter(torch.empty(r, base.in_features))
        self.B = nn.Parameter(torch.zeros(base.out_features, r))   # zero init: starts == base model
        nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))
        self.scale, self.drop = alpha / r, nn.Dropout(dropout)

    def forward(self, x):
        return self.base(x) + (self.drop(x) @ self.A.T @ self.B.T) * self.scale

Catastrophic forgetting mitigation

narrow training can erase general ability: protect it deliberately

1 · Mixed-task balancing (replay)

Blend general-purpose and previously-learned tasks into every epoch so gradients never see only the new domain.

2 · Constrain the update

Low rank, fewer target modules, smaller LR, 1 to 3 epochs, early stopping on a general-capability eval.

3 · Alignment penalty as an anchor

In DPO the beta term penalizes drifting from the reference policy (a KL-style constraint). Higher beta stays closer to the SFT model. In ORPO, the SFT loss term keeps outputs grounded in the preferred completions.

mix_tasks.py
from datasets import load_dataset, interleave_datasets

domain  = load_dataset("json", data_files="domain.jsonl",  split="train")  # your target task
general = load_dataset("json", data_files="general.jsonl", split="train")  # instruction-following replay
guard   = load_dataset("json", data_files="safety.jsonl",  split="train")  # refusals / format guards

# keep every source in the same schema first (e.g. all "messages")
mix = interleave_datasets(
    [domain, general, guard],
    probabilities=[0.70, 0.20, 0.10],     # 10-30% replay is a common range
    seed=42, stopping_strategy="all_exhausted")

# regression gate: run the SAME general eval on base and tuned; block if drop > threshold
# DPO anchor:  DPOConfig(beta=0.1 → 0.3) to tighten drift from the reference
// Bedrock equivalentNo replay sampler, so build the mixture into the JSONL yourself, keep epochs low, keep the learning rate at the lower end of the documented range, and compare the custom ARN against the base model on a general eval before promoting.

Curation checklist

  • Consistency: same output format, tone and labels for the same input type. Contradictory examples cap quality.
  • Coverage: include edge cases, refusals and "I don't know" cases, not only the happy path.
  • Hygiene: dedupe, strip PII, remove test-set leakage, split train/val/test before augmenting.
  • Size: hundreds of excellent examples for style or format; thousands for domain reasoning. Bedrock enforces per-model min/max record counts verify.
  • Loss masking: train on assistant tokens only when possible (TRL: assistant_only_loss with a compatible template) verify version.

Bedrock packaging

  • Customization job output: a custom model ARN. No weights to download or quantize; AWS owns the serving format.
  • Provisioned Throughput: you reserve model units (no-commit hourly, or 1/6-month commitment) and invoke with the provisioned ARN as modelId. You pay while it is provisioned, so delete idle ones.
  • Custom Model Import (bridge): upload merged safetensors for a supported architecture and get a Bedrock-hosted imported model, billed on active usage rather than reserved units verify supported architectures.

import boto3, evaluate, json
rt = boto3.client("bedrock-runtime", region_name="us-east-1")

# ---- backend A: Bedrock custom model (use the PROVISIONED model ARN as modelId)
def gen_bedrock(prompt, model_id):
    r = rt.converse(modelId=model_id,
                    messages=[{"role": "user", "content": [{"text": prompt}]}],
                    inferenceConfig={"maxTokens": 512, "temperature": 0.0})
    return r["output"]["message"]["content"][0]["text"]

# ---- backend B: local Hugging Face checkpoint
from transformers import pipeline
pipe = pipeline("text-generation", model="out/merged", device_map="auto", torch_dtype="bfloat16")
def gen_hf(prompt, _=None):
    out = pipe([{"role": "user", "content": prompt}], max_new_tokens=512, do_sample=False)
    return out[0]["generated_text"][-1]["content"]

# ---- automated metrics
rouge, bleu = evaluate.load("rouge"), evaluate.load("sacrebleu")
def score(preds, refs):
    return {"rougeL": rouge.compute(predictions=preds, references=refs)["rougeL"],
            "bleu": bleu.compute(predictions=preds, references=[[r] for r in refs])["score"]}

# ---- LLM-as-a-judge (judge = a stronger model, NOT the model under test)
RUBRIC = "Score 1-5 for faithfulness to the reference and format compliance. Reply JSON: {\"score\":n,\"why\":\"...\"}"
def judge(prompt, answer, ref, judge_id):
    q = f"{RUBRIC}\n\nPROMPT:\n{prompt}\n\nREFERENCE:\n{ref}\n\nANSWER:\n{answer}"
    return json.loads(gen_bedrock(q, judge_id))

Architectural decisions: when to fine-tune

Each strategy fixes a different class of failure. Choose by what is actually broken, and layer them when more than one is.

Strategy comparison

prompt engineering vs RAG vs fine-tuning / customization

StrategyPrimary purposeData horizon (real-time vs static)Implementation boundary (API-driven vs compute-driven)
Prompt engineeringInstant formatting and task steering: instructions, few-shot examples, output structure, persona.Per-request. Lives in the prompt, changes instantly, no persistence.API-driven. Edit text and call Converse or any model API. No training, no infra.
RAGInject fresh, private, citable facts at query time and reduce hallucination on knowledge.Real-time. Re-index and the next answer reflects it. Updates in minutes.API + data infrastructure. Embeddings, vector store, retrieval, chunking. Still no training compute.
Fine-tuning / customizationPermanently lock in domain-specific reasoning, formatting rules and strict output style, on Bedrock jobs or custom TRL runs.Static. Frozen at training time; new knowledge needs a retrain.Compute-driven. Bedrock managed job or GPU training with TRL, plus evals, versioning and serving.

Signals that point to fine-tuning

  • Long few-shot prompts you pay for on every call, which a tuned model would not need (cost and latency).
  • A strict schema or tone that prompting follows only ~90% of the time.
  • A smaller, cheaper model must match a larger one on a narrow task (also the case for distillation).
  • You have hundreds of vetted examples and an eval set that proves the gap.

Signals that it is the wrong tool

  • The failure is missing or outdated facts: use RAG, tuning will just memorize stale data.
  • No eval set, or fewer than a few dozen clean examples.
  • Requirements change weekly; a retrain per change is not sustainable.

Choosing the execution layer, then shipping

Choose Bedrock whenYou are AWS-native, need IAM/VPC/KMS governance, want minimal ops, and the base model is on the supported list.
Choose TRL whenYou need open weights, DPO/GRPO, custom losses, specific GPUs, or portability across clouds and edge.
HybridTrain with TRL, merge to safetensors, import to Bedrock for managed serving and guardrails.
AlwaysVersion dataset, config and model together. Gate promotion on evals. Keep a rollback ARN or checkpoint.

Pre-launch checklist

  1. Baseline: prompt-engineered base model scored on a held-out eval set.
  2. Dataset: deduped, PII-scrubbed, schema-validated, split before augmentation.
  3. Train: small pilot run first (tiny subset) to validate templates and loss masking.
  4. Evaluate: task metrics, LLM judge, regression suite, red-team prompts.
  5. Deploy: canary traffic, log inputs/outputs, monitor drift and cost per request.
  6. Operate: schedule retraining when RAG-backed facts or requirements shift; delete unused Provisioned Throughput.
